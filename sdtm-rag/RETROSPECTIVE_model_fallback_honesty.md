## 一、保留下来的做法

**1. "先补闸、再引入行为"这条顺序约束是有回报的，不是仪式。**
D6 必须先于 D5 —— 理由是上一轮写下的：补 fallback 会**激活** `model_id` 与 `model_used` 的分叉，
而后者没有任何闸。实践直接兑现：Task 1 补完三条发射端闸之后，复审做变异发现
**累积端仍是零断言**（删掉 ` or model_used`，38 条无一变红），而那个洞的后果恰恰是
"一次真实回退在界面上静默降级成『验证状态未知』"。若按相反顺序，这个洞会在**已经有 fallback**
的代码上潜伏。

**2. 复审的价值不在"复核对方的表"，在"自己加变异"。**
本轮 6 条 Important 里 **5 条**是复审/终审**自加**变异挖出来的，实现者与控制器都没看见：

| 谁抓的 | 发现 | 手段 |
|---|---|---|
| 逐 task 复审 | I-1 `model_used` 累积端零断言 | 自加变异 N7 |
| 逐 task 复审 | I-4 多轮 `models_used.clear()` 全量零红 | 自加变异 V14 |
| 逐 task 复审 | I-5 `Array.isArray` 护栏只有一处有闸 | 自加变异 V-F1b |
| 终审 | I-1 `.unverified` 琥珀色零覆盖 | 自加变异 J17/J18 |
| 终审 | I-2 litellm 对同一模型报两种拼法 | 真 Router + mock 流实测 |

⇒ 派单里那句"**⛔ 不采信实现者的表，自己重做**"是这套流程的承重梁。删掉它，这五条今天都在主干里。

**3. 执行者主动交代对自己不利的事。**
四例，全部无人会查到、报了对自己没好处：
复审自曝"变异期间短暂改写工作树 `app.js`，那几秒用户刷新会拿到变异版"（我派单时的疏漏，随即升为硬约束）；
实现者自曝"本轮先改实现后写闸，没走先红后绿"；自曝"变异框架自身有 bug，变异一度留在磁盘上"；
自曝"报告里 caplog 那半写反了"。
⇒ 这类交代是流程能跑下去的真正原因；**报告里"我没能覆盖的"一节必须强制要求**。

**4. 下级用实测顶回上级方案 —— 本轮两次，两次都是对的。**
Task 3 复审推翻实现者的 M5 前提；终审第 2 轮实现者推翻我的"首见形优先"（实测：只修好 3 种到达顺序里的 1 种）。
⇒ **方案的正确性不由提出者的层级决定，由它在全部输入顺序上的表现决定。**
配套要求也证明有用：终审事后**没读实现者的证明**，直接穷举 6000 组串 × 全部排列做对照，
结论是"我上轮倾向的方案和备选都是错的"。

**5. 环境红线写进每一份派单，且每轮报 PID。**
"绝不碰 localhost:8000"出现在全部 12 份派单里；三轮终审核验前后 `lsof` 报同一 PID（52423）、
同一启动时刻。**这不是靠记性，是靠每份派单重复写 + 每份报告强制声明。**

**6. 前端变异打副本。**
`webchat/` 是 StaticFiles 从工作树现读 ⇒ 改工作树里的 `app.js` **等价于改用户正在用的页面**。
升级为硬约束后，此后 JS 变异全打 scratchpad 副本并每次断言工作树 sha 未变 —— 后续三轮**零窗口暴露**。

**7. 收尾做一次"机械的"自我描述扫描 —— 靠人读拦不住。**
"正文改了、摘要没跟上"本轮出现 **3 次**，位置一次比一次靠外：实现注释 → 测试摘要行 →
**函数签名**（helper 的 `-> str` 与摘要都是旧的，实际早已返回 `SimpleNamespace(text, calls)`）。
前两次靠人读发现，**第三次是用 `ast.get_docstring` 穷举 57 个 docstring 首行才捞出来的**。
⇒ 类型标注比注释更容易被工具和人当成事实，那一处最重。
⚠ 同时：**该留的不要清** —— 另有 5 处"最短形"是**被否决方案的实测记录**（三策略对比表、
期望值改动前后对照），删掉等于抹掉"为什么改"。清的是与当前实现**矛盾**的陈述，不是所有提到旧方案的字。

## 二、必须补上的缺口

**1. L1 未闭合 —— 本轮最大的未验假设，且它是全线的地基。**
`fell_back` 直接吃流式 chunk 的 `.model` 串，而**真实 Bedrock 回退时那个串到底长什么样，全轮零实测**
（三轮累计真实 LLM 调用 **0 次**）。终审零成本收窄了它（`chunk.model` 来源确定、`get_llm_provider`
实际行为、真 Router 跑通 ⇒ "每条答案都误报已回退"在可查路径上已不成立），剩余窄口只有
"Bedrock 会不会报第三种拼法"。**失败是响的**（徽章异常）而非静默，故接受。
⇒ 最小收口方案（需用户点头，走公司额度、不碰 DeepSeek 个人流量）：一次 `max_tokens=1` 的
Bedrock 流式调用，只看首片 `.model`。

**2. 真浏览器从未验证。** playwright 那条闸全程 `skip`；琥珀色只验了 class token 与 CSS 规则存在，
**没有人真的看见过那个颜色**。

**3. 有意留下的三处零覆盖**（都已在 spec 具名，不是遗忘）：
`flagModelName` 的三态只有静态锚无行为闸（后端产不出 truthy-非-true，拒绝为凑红造场景）；
`models_used` 无长度上界（L6，拒绝加截断——截断会悄悄丢掉"谁答的"）；
`/api/ask` 的自证面仍缺 `fell_back`/`models_used`（D11 加重，本轮只钉行为 + 记账）。

**4. `_same_model` 非传递性虽已堵住，证明强度有限。**
"只朝更限定方向增长"的手推证明**未经形式化工具检查**；终审的 6000 组穷举用的是**自造字母表**，
0 反例 ≠ 对一切字符串成立。

**5. 控制器（我）在 plan 阶段连续三次给出无分辨力的变异。**
`fallbacks=[]` 撞 `TypeError`、`sorted(set)` 数据已是字典序、`??` 撞显式布尔。
⇒ **plan 阶段缺一个强制步骤：每写一条变异，先自问"哪种错误实现在这组输入上会产出相同输出"。**
这条已写进 `.work/meta/retrospective.md` 规则 6 成因 D 的检查表，但**它的触发点应该在写 plan 时，不是在跑变异时**。

## 三、关键决策复盘

**D1 — R6（按 chunk 收全 `models_used`）上报用户，而不是自决。** ✅
复审发现 `model_used` 是 last-wins ⇒ 联网多轮里某轮回退、末轮落回主模型会报 `fell_back=false`。
三个处理方案（列表 / 只改布尔 / 维持并记已知限制）**工作量与诚实度各不相同**，且改的是**已获批的线上契约形状**
⇒ 属"不同读法导致实质不同工作"，上报正确。**同时派了与该决定无关的 Task 2，没让整条线停下来等。**

**D2 — `/api/ask` 只钉行为 + 记账，不扩 `AskResponse` 契约。** ✅（终审独立判"裁得对，不改级"）
"用户这轮点的单是 Chat UI 主路径"是**缩小**的理由，而"我们这轮把它的爆炸半径从 1 组扩到 5 组"
是**必须留痕**的事实。⇒ 记账 + 配闸是义务，扩契约是加戏。
⚠ 我在 ledger 里写它"**静默**扩大行为面"**不准确**——行为面变更是有闸的，真正静默的只有那条死路分支。

**D3 — 两处"不加防御代码"。** ✅
`models_used` 不加长度截断（截断会悄悄丢掉"谁答的"，与主旨相反）；
元素级畸形（`[null]`/`[""]`）不加 `filter(Boolean)`（**为不可达路径写防御，下一个人会以为它可达**），
改为在两处护栏写明"元素级契约由 `server/router.py` 收集端的 `if reported:` 保证"。

**D4 — 我被推翻的两次，都该被推翻。**
(a) "首见形优先"：只修好 3 种到达顺序里的 1 种，而我自己要求的是"无条件的话就得真无条件"。
(b) 成因 D 的归类：我把 `fallbacks=[]`→`None` 算作 D，实为"红了但原因不对"，属另一族。
⇒ 与规则 6 初稿"照搬归纳没验算"是**同一个毛病的第二次**。**采纳一条归纳时，归纳本身也要先验算。**

**D5 — spec 初稿两处写错，纠正过程本身留档。**
(a) §3 P6：断言"流中途不会触发 fallback"——把**自己实验的边界**当成被测系统的边界（litellm 实有 `MidStreamFallbackError`）。
(b) §4.3：把 deepseek 串上的"去掉 provider 前缀"**外推**到 bedrock 串并标成"已实测"（实际 `converse/` 保留）。
⇒ 两条是孪生的：**P6 = 「我没测到 ≠ 它不存在」；这条 = 「我在 A 上测到 ≠ 它在 B 上也成立」。**
⚠ 而我是**在同一份 spec 里写下前一条教训之后**，又在下一层犯了后一条。
唯一让它没变成生产缺陷的原因：判据本身**不依赖前缀被剥掉几层**——那不是运气，是选判据时刻意不去数层数；
但若当初选了"剥两层再比"，今天就是一个生产缺陷。

**D6 — 上线时序：Task 5 之前不许重启，之后解禁但**带条件**。** ✅
R2 的代价（答题可能落到 DeepSeek 个人流量）先于 R4/R5 的条件（诚实标注）落地 ⇒ 中间窗口必须封。
解禁的三条论证由复审给出（差分实测：老后端下徽章/⚑/存档逐字节相同）。
⚠ 但终审 I-3 指出：**那三条论证全部落在"新前端 + 老后端"这一个方向上**，
而"**老前端 + 新后端**"（一个已打开、始终没刷新的 tab 持有旧 JS）从未被分析——那种情形下真回退
= C-1 原样。⇒ 已补 spec §5 B3 + §7.5 的解禁条件（**重启后已打开的标签页必须硬刷新**）。
**通用教训：兼容性分析要问"哪两端会各自处在哪个版本"，而不是只问"我这一端换了新的会怎样"。**
