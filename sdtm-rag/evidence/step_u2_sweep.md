## 1. 命令 (逐字, 全部零 LLM 生成)

```bash
cd sdtm-rag
P=data/study/st01/eval/test_set_docs_v1.yml
for N in 0 3 5 8 10 15; do
  ./.venv/bin/python -m eval.run_eval $P --retrieval-only --hybrid --study-lookup \
    --federated --corpus study --study-docs --doc-seats $N \
    --output data/study/st01/eval/runs/u2_docs_N$N.json
done
```

`--corpus study` 强制判库是为了**隔离判库变量** —— 本表量的是接线, 不是路由。

## 4. 生产 N 的裁定与理由

**N = 8。**

- **为什么不选更小**: N=5 省 28% token, 但丢 **11.67pt** 召回 (1.0000 → 0.8833);
  N=3 省 45%, 丢 13.33pt。doc 轨的全部目的就是让这些内容答得出来。
- **为什么不选更大**: N=10 / N=15 实测**零召回增益** (都已是 1.0000), 却继续把
  context 从 3.17x 推到 3.68x / **5.19x**。纯成本。
- N=8 是**召回天花板上的最小 N** —— 这个"最小"是实测出来的, 不是猜的 (N=8 满分 30/30,
  N=5 满分 25/30)。

⚠ **代价必须同写**: 每一道判到 study 的题, context 都涨到 **3.17 倍**, 包括那 48 道
根本不需要手順書的卡片题 —— 它们拿到 8 条纯噪声。这笔代价是否伤答案由 Task 8 双臂裁定,
**本表不能回答**。

## 5. 本表看不见什么 (硬规矩 19)

1. **只量 gold 召回, 不量答案质量** —— N=8 的 1.0000 不意味着答得出来 (Task 8 的事)。
2. **强制 `corpus=study`, 不含判库损耗** —— 生产档口径见 `step_u2_rulers.md` 尺子③。
3. **单遍** —— 各档只跑一遍。检索有非确定性 (spec §5.2.1, 源在 embedding API,
   实测同一 query 6 次得 2 种向量); 逐档单遍数字可能有 ±1 题的抖动。
   **但"与 U1 逐档逐位相同"这件事本身跨 6 档同时成立, 靠巧合达成的概率极低。**
4. **context 成本按 `cl100k_base` 估算** —— 生产答题模型走 Bedrock (Claude), 分词器不同,
   token 数只可作**相对比较** (倍率), 不可当账单。
5. **不含 `both` 判库档** —— `both` 下 context = 8(cdisc) + 8(cards) + N, 未量。
