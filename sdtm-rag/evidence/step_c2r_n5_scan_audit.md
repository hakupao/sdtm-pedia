## 2. 勘误: 已知真阳性的成因描述错了 (对 N4 审计 §7 的更正)

N4 审计 §7 与其伴生件 §0.9 写:「该活动 OID 在本题检索到的 16 个 study 源里出现 **0 次** —— 不在上下文里, 是模型自己造的。」

**实测不成立。** 该 OID 在 16 个源之一的**另一张同表单字段卡的「非表示アクティビティ」行里出现 1 次**。

成因是**测量口径, 不是检索缺席**:

| 层 | 该 OID 出现次数 |
|---|---|
| run json `response.sources[].text_preview` (16 段) | **0** |
| 同 16 个源的**磁盘全文** | **1** (在另一张卡的非表示名单行) |
| 向量库里那张卡的 chunk 全文 (539 字符, 整卡一块) | **1** |

`server/router.py` 三处一律写 `text_preview = c.text[:300]`。字段卡模板把「非表示アクティビティ」行
排在 frontmatter + 表头 + 型 / Control / Codelist 之后, **恒定落在 300 字符之外**。
所以「grep run json 的 sources」= grep 16 段 300 字符摘要, 必然 0 次; 而**进模型的是整卡**。

**结论: 该条仍是真阳性, 但性质要改写** —— 不是「凭空造一个上下文里没有的 OID」,
而是**把同批检索结果里另一张卡的非表示名单成员, 移植到被引卡的名单上**。
真值方向仍然相反 (被点名的活动恰是被引卡的显示活动之一)。
闸给的类别 `CONTEXT_MISCITED` (不在被引文件、但在本 run 其他 study 源) **比 N4 审计的描述更准确**。

> **独立性说明**: 本条是 judge 自己从磁盘卡片全文 + 向量库 chunk 全文复算得出的, **先于**读到 writer 侧的改动。
> 事后核对: N5 Writer 已在 `step_c2r_n4_audit.md` 末尾追加同方向的 Erratum 段, 与本节结论一致。
>
> **下游必须跟着改的地方**: N4 审计 §9-6 与伴生件 §1.1.1 的「不在上下文里」「凭空」措辞 (§7 已由 Erratum 覆盖);
> **PLAN §10 的 PATTERN 描述**同样引用了「16 源 0 次」这个错数, 建议改成「不在被引卡、在同批另一张卡」。
> **判分结论不受影响** —— N4 §8.1 那条依赖的是「方向与真值相反」, 与「是否在上下文」无关。
> **但对修法的含义变了**: 这不是「幻觉出一个不存在的东西」, 而是**同批上下文内的串卡串行**,

## 6. n=3 的诚实读法 (交接必读)

1. **卡片层闸是第一个有真捕获的闸**。本验证集: 标红 9 条里真阳性 2 条 (精确率 22.2%);
   画面层 N2 闸三轮累计是 **0 真捕获 / 6 假阳性** (N4 §6)。方向明确变好, 但**基数只有 2**。
2. **已测到的召回是 2/3** (三条独立核实的真错误, 闸抓到 2 条, 漏 1 条, §4.2)。这不是判据 ① 的口径
   (那条只问已知那 1 条), 但它是**本次审计能给出的最诚实的召回数字**, 交接必须带上。
3. **三条真错误同一病根**: 都是**在同批检索结果内部串卡** —— 把 A 卡的名单成员、或 A 卡的名单属性,
   挂到 B 卡出典上或推广到别的组。`UNGROUNDED` 与 `BAD_SOURCE` **在 289 个单元上各 0 次**
   ⇒ 本项目 study 层的错误形态是**串卡**, 不是**无中生有**。
   对 prompt 规则的含义很直接: 「只写被引文本里实际有的」这条**打得准**; 「不在文脈就说不在」那条**本轮无靶**。
4. **同一模型在同一道题的 A / B 两臂各犯了一次同型过度推广** (§3.1 与 §4.2)。
   闸在 B 臂抓到、在 A 臂漏掉, **差别不在错误本身, 在被引卡的名单里恰好有没有那个 OID** ——
   **这说明闸的命中带有相当大的偶然成分**, 不能读成「闸能识别过度推广」。
5. **四条纯假阳性有三个不同成因, 且都是设计已写明的盲点**: 跨语料比对句 (#1)、位置指称 (#6)、
   单元切分吞掉画面句 (#8/#9, 两条)。**其中单元切分那条占了 2/4** —— 触发条件是
   「画面出典排在卡片出典**之后**」, 这是 N3 之后答案的常见排版, 属**可预期会重复发生**的成因, 不是偶发。
