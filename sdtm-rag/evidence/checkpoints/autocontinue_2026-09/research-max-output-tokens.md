## Key findings on litellm mechanics (litellm 1.88.1, files under `.venv/lib/python3.14/site-packages/litellm/`)

1. **Anthropic-native config path** (`llms/anthropic/chat/transformation.py:267-291`, used by `anthropic/*` model ids): if the caller omits `max_tokens`, `AnthropicConfig.get_config()` calls `get_max_tokens_for_model(model)`, which calls the public `litellm.get_max_tokens(model)` and falls back to `DEFAULT_ANTHROPIC_CHAT_MAX_TOKENS` (env-overridable, default `4096`, `constants.py:418-419`) only if the model is unmapped. For all four `anthropic/*` ids here, the model **is** mapped, so the real max (128K/128K/64K) gets injected automatically — no truncation risk from omitting `max_tokens`.
2. **Bedrock Converse path** (`llms/bedrock/chat/converse_transformation.py:1103-1128`): the only place litellm auto-computes `maxTokens` is the "thinking enabled + max_tokens absent" branch, which sets it to `thinking_token_budget + DEFAULT_MAX_TOKENS(4096)` — a fixed small buffer, not the model's real ceiling. Outside that branch, if `max_tokens` is never passed, `maxTokens` is **absent from the request entirely**; AWS's own Converse API defaults it server-side to the model's max, per the [InferenceConfiguration reference](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InferenceConfiguration.html) ("default value is the maximum allowed value for the model"). A community AWS re:Post thread notes this can quietly reserve the model's full TPM quota if left unset — a cost/throughput risk, not a correctness one.
3. **DeepSeek/OpenAI-compatible path** (`llms/deepseek/chat/transformation.py` → `llms/openai/chat/gpt_transformation.py`): no default injection at all. `max_tokens=None` is passed straight through and dropped from the JSON body; whatever DeepSeek's server does with a missing `max_tokens` is out of litellm's control and undocumented here.
4. **No client-side clamping anywhere.** Grepped `litellm/` for exceeds/clamp logic tied to `max_tokens`; found none for Bedrock Converse or DeepSeek. An over-limit `max_tokens` is passed straight to the provider, which is expected to reject it (Bedrock Converse: `ValidationException`/400; DeepSeek: standard OpenAI-style 400) rather than litellm silently truncating or erroring first.
5. **`litellm.get_max_tokens()` has a prefix-stripping bug for this project's exact Bedrock strings.** It doesn't recognize `bedrock/converse/global.anthropic.claude-opus-5` (or the `global.openai.gpt-5.6-*` equivalents) even though the underlying `litellm.model_cost` dict has correct entries once the `bedrock/converse/` prefix is manually stripped. Don't rely on `get_max_tokens()` at runtime for these exact id strings — it will throw.

## Recommendation

- For the four `anthropic/*` models (default/fallback-adjacent/hard/light), it's safe to **omit `max_tokens`** and let litellm inject the correct per-model ceiling (128K/128K/64K) — verified via source reading, not just `get_max_tokens()`.
- For the four `bedrock/converse/...` selectable models, **don't rely on litellm's implicit behavior for cost/quota control**: explicitly pass `max_tokens=128000` (Opus 5, Sonnet 5, confirmed by AWS docs) and, until AWS/OpenAI publish an explicit ceiling for GPT-5.6 Terra/Sol on Bedrock, treat **128,000 as an unverified working assumption** (sourced only from litellm's static `model_cost`, not a primary AWS/OpenAI doc) — validate empirically (send a request with `max_tokens=128000` and confirm no `ValidationException`) before trusting it in production.
- For `deepseek/deepseek-v4-pro`, explicitly set `max_tokens` on every call (e.g. cap it well under the reported 384K working ceiling, sized to your actual use case) rather than relying on an undocumented DeepSeek server default — this path is the fallback model and the one place litellm injects nothing at all if it's left unset.
- Do **not** call `litellm.get_max_tokens()` on the literal `bedrock/converse/...` strings from `config.py` for runtime decisions; it errors on all four. If you need the ceiling programmatically, strip the `bedrock/converse/` prefix and look the resulting id up in `litellm.model_cost` directly (or hardcode the confirmed 128000 values for the two Anthropic-on-Bedrock entries).
- Because `deepseek/deepseek-v4-pro` is the `fallback_model` sharing request kwargs with the primary Anthropic-path call, make sure whatever `max_tokens` value is set for the primary Anthropic request (up to 128K) is also valid for DeepSeek's reported 384K ceiling — it is, with headroom, but don't assume a value tuned for Anthropic silently works for every future fallback target without re-checking that target's own ceiling.
