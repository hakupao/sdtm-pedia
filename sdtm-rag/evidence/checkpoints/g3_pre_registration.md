## 1. 唯一要回答的问题

`resolve_events` 通道**接线与否, 对真实用户有没有差别**?

C3 §8 已把话说死: 这个问题**只能由真实提问数据回答, 不能由再出一版尺子回答**。
理由: 现有 33 题 event gold 由知道 catalog 的人出, 「题面含 OID」的比例很可能显著
高于真实提问; **19/33 的触发率是尺子上的, 不是世界上的**。

## 2. 判定单位与 PASS 定义

**判定单位 = 一条真实提问原话。**

一条提问记 **PASS** 的**充要条件** (两条都要满足):

1. `resolve_events(原话)` 返回**非空**;
2. 返回集合里**至少一条**是该提问真正要的答案。

**第 2 条由用户逐条勾选, 我不自判。** 理由与 C2-pre §5 同: 自己出题自己判会重演本仓
已多次出现的「尺子饱和」闭环。我只提交每条的机械事实 (返回了什么 / 靠哪一层 / 几条),
「这条算不算答对了」留白给用户。

## 3. 无条件记录 (不论 PASS 与否, 逐条都记)

| 字段 | 含义 |
|---|---|
| `has_oid_literal` | 该条原话里是否出现 catalog 四池中任一 OID 的**字面** (程序化判定, 有界匹配) |
| `hit_tier` | 命中靠哪一层: Tier 1a (event/activity OID 精确) / Tier 2 (item OID → `collect_scope` 减法) / Tier 1b (form OID → 原始清单) / 无 |
| `n_returned` | 该条返回条数 |

这三个数**独立于 PASS 判定**, 用于回答「本通道只认标识符字面」这个已知性质在真实提问
上到底意味着什么 (C3 §7: 砍掉 Tier 3 后 14/33 题返回 0 条)。

## 4. 自毁条款

- **S1**: 10 条里 **PASS < 10** → **G3 不达标, C4 不接线**。
  门槛沿用 C3 §8 原文的「≥10 条真实用户提问能被本通道回答」, **本轮不改阈值**。
- **S2 (读法约束)**: 若 PASS 的条目里 **≥8 条 `has_oid_literal = true`**, 则即使凑够 10 条,
  报告须**显著标注**「本通道的适用面依赖用户打 OID」, **不得**读作「真实需求已证实」。
- **S3 (防凑数)**: 用户提供的条数**只能是真实回想起来的全部**, 不许为凑 10 条现编。
  不足 10 条 → 如实记不足 → **判 G3 不达标**。
  **「不足 10 条」这个结果本身比凑够更有信息量** —— 它直接指向 C3 §8 的另一半结论:
  接线与否对用户无差别, C4 的正确动作是不做。

## 6. 本判据看不见什么 (硬规矩 19)

1. **PASS 只证明「本通道离线返回里有对的东西」**, 不证明接线后它在检索里活得下来 ——
   union-add 之后还要与卡片抢席位, 那是 **G2** 管的, G2 至今 **未测**。
2. **样本是单一提问者**。10 条来自一个人的真实工作, 不是全体用户分布; 代表性无法由本判据
   保证, 也不该被本判据的 PASS 反过来论证。
3. **S3 无法程序化验证**。「是真实回想还是现编」只能靠自律, 本判据没有任何闸能查出来。
4. **PASS 集合天然偏向含 OID 的提问** —— Tier 3 名称层已在 C3 §7 移除, 通道**只认标识符
   字面**。因此 `has_oid_literal` 的高比例是**通道能力边界**的反映, **不得**反过来读成
   「用户就是这么问的」。S2 就是为堵这个读法而设。
5. **全部判定是离线的**: `resolve_events` 至今零生产调用方 (`rag.py` / `main.py` /
   `routing_signals.py` 均不调用), 本轮数字不是线上实况。
