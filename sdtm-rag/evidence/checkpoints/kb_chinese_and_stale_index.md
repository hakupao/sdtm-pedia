# VARIABLE_INDEX 中文骨架溯源 + 部署索引长期陈旧 (2026-08-04)

> 起因: CJK bigram 切词工作中发现 CDISC「英文」主库有 66/4146 chunk 含 CJK, 用户质疑
> 「按理说应该是全英文来的」→ 溯源调查 → 牵出一个更大的运维问题
> 红线: 本文档只含统计与结构描述

## 1. 中文的来源: 生成脚本硬编码, 非源 PDF

`knowledge_base/VARIABLE_INDEX.md` 的 431 个中文字符全部来自生成脚本
`.work/04_optimization/scripts/generate_variable_index.py` (commit 86d761a) append 的
**骨架串** —— 表头 / 章节标题 / 说明文字。脚本读的是英文 `spec.md`, 数据本身一直是英文。

违反 CLAUDE.md 约定「Knowledge base content is in English」。该文件被切块进向量库,
属 KB 内容而非工作文档 → 已全部改英文。

**未改**: `ROUTING.md` (1141 中文字) / `INDEX.md` (46) —— 二者**不进向量库**, 而是
整file注入 system prompt (rag.py:132-137), 中文是写给模型的指令, 性质不同。

### 转换的验证 (两种独立方法交叉)

| 方法 | 结果 |
|---|---|
| 反向翻译后逐行 diff (执行者) | 2005/2005 行完全一致 |
| 直接抽取数据行比对 (复核者, 独立实现) | 1658 行中 12 行差异, **全部**只是骨架 (所有域→All domains / 共N个→N total) |
| 星号单元格 (Role/Core 不一致标记) | 15 个逐一保留 |

### 顺带堵住的两个隐患

1. **生成脚本静默漂移**: commit 45c8e9b 曾手工修正 9 个 Role 星号但**没回写脚本** ——
   天真重生成会静默回退该已验证修复。规则 (首条目值 + `*`) 已固化进脚本。
2. **三个消费方按中文表头做锚点解析**: `chunkers/variable_index.py` 与 `terminology.py`
   的 §H2 锚点 (实测: 不改则新文件只切出 **1 chunk 而非 222** = 灾难性检索回归),
   `reconcile_meta.py` 的表头锚点 (被全量测试捕获)。均改为新旧双模式兼容。

## 2. 意外发现: 部署中的向量库长期陈旧

重灌主库后 chunk 数 **4146 → 4303 (+157)**。溯源: 全部 157 个增量来自
`VARIABLE_INDEX.md` 一个文件 (**65 → 222 chunk**)。

**排除法定位病因** (三组合实测, 均 222):

| 组合 | chunk 数 |
|---|---|
| 旧 chunker 代码 × 旧 (中文) 文件 | 222 |
| 新 chunker 代码 × 旧 (中文) 文件 | 222 |
| 新 chunker 代码 × 新 (英文) 文件 | 222 |

→ 本次改动**没有**影响切块数; 部署索引里的 65 来自**更早的状态**, 即索引长期落后于
chunker 的演进, 且从未有人重灌。生产 RAG 一直在用一个把变量索引欠切 70% 的库回答问题。

### 重灌的影响 (CDISC 140 题, retrieval-only + hybrid)

| | recall |
|---|---|
| 重灌前 (陈旧索引) | 74.3% |
| **重灌后** | **80.0%** |

逐题: 改善 14 题 / 退步 4 题 / 不变 122 题。

**退步的 4 题共享同一机制**: VARIABLE_INDEX 完整入库后在变量类问题上**挤占 top-k**,
把域 `spec.md` 的 gold 挤出。但其中至少一题 (问某变量的码表) 的答案**本就在
VARIABLE_INDEX 里** —— gold 只认域 spec, 属题集口径窄, 不全是真损失。
与 study 轨 golden set 暴露的"gold 记录窄于正确答案"是同一类问题。
