## 摘要

| 版本 | 结构假设 | 映射覆盖 | 取值结果 | 判定 |
|------|----------|---------|---------|------|
| v1 `e17711d` | 单行表头, 列头 = Item OID | 10/959 (1.0%) | 10 个"值" | ❌ 假设证伪 |
| v2 `d6bfd1a` / `a59f47d` | 单行表头, 列头 = 日文 label | 671/959 (70.0%) | 671 个"值" | ❌ **全是 OID 回声** |
| v3 (本轮) | **双表头行**: 行1 label / 行2 OID, 数据自行3起 | **872/959 (90.9%)** | **0 个值 (零数据行)** | ✅ |

"取到的东西是否像一个实例值"的语义核验 —— 而它们 671/671 全部等于该列自身的 Item OID。

## 为什么两轮 review 都没抓住

1. **测试用的合成 fixture 复制了错误的结构假设** (单行表头), 于是测试越绿, 越是在确认一个
   错误的世界模型。合成数据只能验证"代码是否按我理解的方式工作", 不能验证"我的理解是否正确"。
2. **只做了结构核验, 没做语义核验**。冒烟只打了 `matched-items: 671 / 959` 这类计数, 从未
   问一句"取到的值长什么样"。而"值 == 列自身 OID"这种形态, 只要看一眼分布就会立刻暴露。
   —— 这正是规则 A (语义抽检) 存在的理由: 计数是结构证据, 不是业务证据。
3. **v2 的一个观测其实已经在报警, 但被误读成了特性**: "671 个 item **每个恰好 1 个去重值**,
   2 值及以上 0 个"。真实数据不可能有这么整齐的分布, 这本该是"你读到的不是数据"的强信号,
   却被写成了"DEMO 每 sheet 只有 1 行数据"的佐证。**异常整齐的分布要当作故障信号, 不是特性。**

## 沉淀为代码的防线 (v3 已落)

- `_is_oid_header()` —— 行 2 是否为 OID 表头的确定性判据 (非空单元格 ∈ OID 全集比例 ≥ 0.9;
  真实 100%), 而非硬编码"行 2 一定是表头"。
- **反回声闸** —— 采样值 == 该列自身 OID 即判解析失败, 剔除并计入 `echo_dropped`。
  这条闸若在 v2 就存在, 671 个假值会当场全部落进计数器。
- `conflict_row2_label` —— 权威层与 label 佐证层结论不一致的计数 (真实 0)。
- `unknown_sheets` / `data_rows` / `per_sheet_data_rows` —— 静默失效观测哨。

## 下次做同类任务的检查单

1. 拿到任何"从真实文件抽取值"的任务, **先看抽出来的东西长什么样**, 再看抽出来多少个。
2. 合成 fixture 的结构必须先经真实文件的结构核验, 不能直接照抄 brief 的假设。
3. 分布异常整齐 (全部恰好 1 个值 / 全部同长度 / 全部同前缀) = 故障信号, 不是特性。
4. 值域自反检查要做成断言 (值 == 键名 / 值 == 列名 / 值 == OID 一律视为解析失败)。
