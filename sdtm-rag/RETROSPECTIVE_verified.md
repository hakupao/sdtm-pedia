## 1. 保留下来的做法 (有效, 下次照做)

- **判据 + 自毁条款在任何数据到达前单独 commit** (`46fd756`): 之后判据被改 (V-1) 时, "改了什么 / 谁裁定 / 阈值动没动 / 变松变紧" 有一个不可抵赖的基线可比。没有这条, V-1 修订就无法与"挑数字"区分。
- **自毁条款是本单元最值钱的设计**: S1 (码 < 20 ⇒ (a) 无分辨力) 和 S2 (四模型 (a) 全同 ⇒ 题集饱和) 在动手前就堵死了「PASS 但什么都没测到」的假 PASS 通道。S1 事后看四模型码数 454/271/140/117 都远超 20, 但 GPT 系只有 opus 的 1/4 – 1/3 (140/117 vs 454) ⇒ 分母警告已写进汇报连带项。
- **(b) 层人判 + 对抗抽样 (5 条抽自裁判说"干净"的)**: 裁判偏保守 (32 条上 12 条报警全假阳性, 20 条 consistent 零漏网) 这个事实**只有人判兜底才知道**
  (⚠ 其中 24 条的判定是一句无明细的「全部pass」⇒「零漏网」的证据强度受限, 见 §2 第一条)。LLM 代判 = 用裁判查裁判, 结构上测不到漏网。
- **口径分歧用数据判而不是用论证判**: V-1 争论"哪个检索口径算'上下文'"时, 决定性证据是重建 top5 与落盘 `top5_sources` 的吻合率 (生成口径 102/102, 旧写死口径 0/102), 不是谁说得更有道理。修完还加了两道只会更容易 FAIL 的闸 (`ReconstructionMismatchError` / `DegenerateContextError`) 并用变异实证闸有牙。
- **每一步都落可复跑命令 + timing.txt 内含精确 CMD**: 三模型并行跑的 `run_<tag>.timing.txt` 把完整命令行写了进去, 下次不用再从 summary 反推参数 (本轮 opus-5 就是反推的)。
- **成本报数按"生成 + 裁判"两半算**: 早期沟通只算了生成那一半 (408), 实际 816。发现后立刻在 checkpoint / 交接 / 汇报三处改口。
- **「实测过的东西也可能测错了对象」** (worklog 09-03 唯一标为「教训」的条目): (a) 层第一次跑出 8 条 ungrounded, 数字真实、脚本没 bug、命令可复跑, 但被测对象 (重建的上下文) 是错的。**可复跑 ≠ 测对了东西**; 「实测」除了附命令, 还要附「测的是哪个对象」的证据 (本例即保真闸)。
- **(b) 层也有自己的假 PASS 闸**: `entries_from_report` 拒绝回退到 600 字符的 `answer_preview` —— 拿 preview 问裁判, 大部分归属断言落在截断外 ⇒ 裁判大面积判「无断言」⇒ (b) 恒 PASS, 且看起来和真通过一模一样。与 (a) 层两道闸对称, 两层都要设防。
- **人判结果要追问「是否逐条看了」**: 第一轮用户首答「看了一些, 都 PASS」, 追问后用户要了路径重看一遍再确认。这个动作有效 —— 但没制度化, 第二轮就没做 (见 §2)。
- **跨 session 交接文档写「⛔ 新 session 不要做什么」**: 09-04 交接的 §0 明写"不要代判、只问用户拿 8 条", 09-06 的 session 照做了。交接的价值在阻止错误动作, 不在复述状态。

## 2. 必须补上的缺口 (下次改进)

- **人判包要自带回填表**: 第一轮 (opus-5 8 条) 用户首答「看了一些, 都 PASS」, 追问后重看确认; 第二轮 (三模型 24 条) 只回「全部pass」一句, 未追问。两轮都**没有逐条 PASS 的落盘明细** (FAIL 理由栏为空是合规的 —— 无 FAIL; 缺的是 PASS 也逐条留痕), 无法区分「看了全 PASS」和「扫了一眼」。下次人判包末尾放一张 `| 题 | PASS/FAIL | 理由 |` 的空表, 让判定本身成为落盘物, 追问也写进流程而不靠临场。
- **人判盲性被两个不同的洞破坏, 且第二个洞让第一次泄漏永久有效** (Rule D 审阅抓出根因, 本 retro 初稿写错了):
  - 洞 1 (第一轮, 终端): 打印了「裁判报警项在人判包里的**位次**」。洞 2 (第二轮, 工具输出): 打印了 `class_scan_<tag>.json` 的 `sample_ids`, 它是 clean 段 + flagged 段拼接 ⇒ 顺序即 verdict。两个洞不同, 初稿提的修法 (`sample_ids` 按 blind_order 落盘 / 改名) **只堵洞 2**。
  - **根因**: `blind_order` 用固定 `seed=0` 做 `random.Random(seed).shuffle`, 而 `pick_sample` 恒返回 clean[0:5]+flagged[0:3] ⇒ 输入形状恒定 ⇒ **置换恒定**。审阅实测四份人判包报警项位次**全是 (3, 7, 8)**。所以第一轮泄漏的位次对后三轮同样成立 —— 暴露面不是「两轮」, 是**四轮全部**。
  - 修法: 置换 seed 随 tag 派生 (与抽样 seed 解耦 —— 预登记锁的是抽样 seed, 不是置换); `sample_ids` 按 blind_order 落盘; 「报警项位次」与 `sample_ids` 列入禁打印项。
  - 本轮结论不翻: 32 条全 PASS, 锚定方向 (更易判 FAIL) 与结果相反。这是**前向成本** —— 不修, 下个单元继承一个坏的 blind。
- **判据修订后, 旧跑与新跑上限不齐 (B-2)**: V-2 钉死 `max_tokens=8192` 是对的, 但 opus-5 那轮跑在修复前 (4096, q36/q83 截断) 没有重跑。四模型比较时这是已知不齐, 抹平要 102 次生成。下次任何影响生成侧的修订, 先问"已跑的要不要重跑", 把答案写进记录, 不要默认"影响有界"。
- **`pytest -q` 与 pyproject `addopts = "-ra -q"` 叠加成 `-qq`, 汇总行消失**: 本轮一次后台 pytest 被提前中断, 日志末尾只有 SKIPPED 行, 差一点被读成"通过"。之后查出是 `-qq` 吞了 `N passed` 行。规则: 测试通过的证据是 **`N passed` 那一行 + exit 0**, 缺任一都不算; 本仓库跑 pytest 不要再手加 `-q`。
- **`nohup ... &` 起的后台进程随工具 shell 退出被杀** (仅本 session 观察, 未落盘证据): 第一次 pytest 就是这样死的 (三个 run_eval 用同法起却活了, 因为跑得久还是碰巧, 未查)。长任务一律走 `run_in_background`, 不靠 nohup。
- **索引生成脚本迟到了一轮**: opus-5 的对照索引是手工 python 一次性生成、没入库; 三模型轮才补 `make_human_packet_index.py` 并对 opus-5 复算零 diff 证明等价。规则: 任何给人看的派生物, 第一次生成就入库脚本。
- **`code_grounding_on.json` 是共享输出路径**: (a) 层脚本固定写 `eval/prod_wirein/code_grounding_on.json`, 跑第二个模型就覆盖第一个的落盘。本轮靠手动 cp 到 `verified_runs/code_grounding_<tag>.json` 救回, 且工作区里 opus-5 那份被覆盖过一次 (已 checkout 还原, 未进 git 历史; 仅本 session 观察)。应让脚本按 report 的 tag 命名输出。
- **生产服务读启动时的 config**: `verified` 翻了之后 `/api/info` 仍返回旧值, 直到 kickstart。这条已写进 worklog, 但 config 里带 `verified` 的字段应有注释提醒"改后需重启", 或 `/api/info` 里带 config 加载时间戳。

## 3. 关键决策复盘

- **V-1: 看过数据后改判据脚本 (用户 09-03 裁定, 方向对被测对象有利)**: 这是本单元最需要摆在明面上的决策。支持它的不是"结果更好看", 而是 (i) 判据文本说的是 grounded 在**上下文**, 而上下文只有一个定义 — 模型当时看见的那个, 旧脚本 0/102 还原; (ii) 阈值一个没动; (iii) 新脚本只更容易 FAIL。若当时选择"脚本即判据, 维持 FAIL", 会把 8 条口径差假阳性当真 mis-cite 报出去 —— 那是另一种不诚实。**教训**: 预登记应该锁的是判据的**语义** (码要在模型看见的上下文里), 而脚本的实现细节 (重建口径) 是语义的载体, 载体有 bug 时修载体不是改判据; 但必须以"修订记录 + 复跑 + 变异"三件套的形式修。
- **sonnet-5 那 1 条 ungrounded 判 FAIL 不放松**: `C66742` 是 NY 码表的真实码、配对正确, 只是不在 q35 的 top-15 里。有人会说"码是对的为什么 FAIL"。答案: 判据测的是**接地**不是**正确**; 一个能从参数知识里拿出正确码的模型, 同样能拿出错误码, 而接地判据恰恰是为了不依赖"它这次碰巧对了"。0 阈值放松到 1 就没有阈值了。代价是 sonnet-5 挂 false 徽章, 用户可选但被提醒。
- **两道前置闸, 归属要分清**: (i) **先跑 opus-5 一个模型**而非四个一起 —— 用户裁定 A (09-02 前, commit `7892e67` 正文); (ii) **再以 8 条人判 / S3 作为烧 612 次的前置闸** —— 09-04 交接 §4 建议, 用户 09-06 采纳。逻辑: 若 opus-5 的 S3 触发 (裁判漏网), 同一裁判给三模型做对抗抽样就不可信, 应先换裁判而不是先烧。S3 未触发 ⇒ 才开跑。「先验证工具再用工具」省下的是**错方向的 612 次**, 不是钱本身。
- **知道有洞、有零成本补救、选择不补**: 洞 1 泄漏后, 交接 §7 给了 `--reuse-scan` 零调用重出换序包的补救, 两轮都**没用**, 用户对「判前是否看到」也未表态。当时的理由是「锚定方向与结果相反, 不改结论」—— 对本轮成立, 但等于把盲性从流程保证降级为事后论证。以后有零成本补救就做, 不拿结果方向替代盲性。
- **三模型并行而非串行**: 三个不同 Bedrock 模型无共享限流, 并行 23 分钟跑完 (串行约 43 分钟)。共享的只有 OpenAI embedding, 无异常。风险是三跑同时写 `code_grounding_on.json` —— 但 (a) 层是跑完后串行做的, 未撞。
- **合并 main + 重启生产在用户一句授权后立即做, 不再确认**: 合并是 ff、测试 2049 passed、`/api/info` 前后对比可回滚, 属可逆动作; 分支删除被权限闸拦下则如实报告让用户自己跑 (后用户再次明确要求才代跑)。边界: 系统状态改动要有用户话在前, 但有了就不重复问。
- **没做的: 重跑 opus-5 抹平 B-2、裁判换模型交叉验证、q35 这类"参数知识正确码"是否系统性**: 三者都是 102+ 次调用量级, 且当前数据不支持它们会改变任何一个 `verified` 值。留作未来单元, 触发条件是 dogfood 出现相关失败案例, 不是"为了完整"。
