# 阶段性反思：Issue 1 & Issue 2 根因分析与预防机制

> 创建日期: 2026-04-15
> 适用范围: 本项目全阶段 + 同类 AI 辅助知识库项目

---

## 1. 两个 Issue 的共性根因

Issue 1（图像页码偏移）和 Issue 2（内容空洞过验证）表面不同，但共享同一条因果链：

```
AI 能力边界被高估 → 流程设计没有为 AI 弱项设置补偿机制 → 产出中的缺陷被当作正确结果固化
```

| 维度 | Issue 1: 页码偏移 | Issue 2: 内容空洞 |
|------|-------------------|-------------------|
| **AI 被信任做什么** | 视觉读取 PDF 精确定位页码 | 修复内容缺失并自行判定完成 |
| **AI 实际做到什么** | 只能估算（±2~4 页） | 只能重建骨架 + 打占位标记 |
| **为什么没被拦住** | 无程序化页码校验机制 | PASS 标准允许"标记了缺失"通过 |
| **谁发现的** | 用户人工抽查 | 用户人工对照 PDF |

---

## 2. 三个前置条件（缺一不可）

### 2.1 用定性标准代替定量标准

Issue 2 的 PASS 判定是"结构正确 + 已有内容准确 + 缺失已标记"——回答的是"看起来对不对"，而不是"覆盖了多少"。

如果当时有行数比值（md 行数 / PDF 页数），340 行 ÷ 38 页 ≈ 9 行/页，就能立刻发现异常。修复后的 ch04 是 654 行 / 38 页 ≈ 17 行/页。

### 2.2 自写自判（same-context self-validation）

两个 issue 的验证/修复都在同一个 agent 上下文中完成：
- 写的 agent 知道自己标记了占位，但认为"标记了就算处理了"
- 判的 agent 看到结构完整、标记清晰，就给了 PASS
- 本质上是让考生给自己批卷

后来修复计划中引入的"写/审分离 + 独立 subagent 复核"正是针对这个问题，实践证明有效（8/8 节通过独立复核）。

### 2.3 把 AI 的估算值当成事实值

Issue 1 中，Sonnet agent 标注的页码本质是"估算值"——Read tool 返回内容中页码边界不清晰，agent 只能推断。但流程中没有区分"精确值"和"估算值"，全部作为权威数据写入了 page_index.json 和 image_inventory.md。

## 3. AI 能力边界认知

| AI 擅长 | AI 不擅长 |
|---------|-----------|
| 结构化数据转换（xlsx → md） | 精确定位 PDF 页码 |
| 内容比对（找差异） | 判断"够不够完整" |
| 格式校验（标记、节号） | 衡量覆盖率 |
| 批量处理重复模式 | 评估自己的产出质量 |

---

## 4. 六条预防规则

### 规则 1：定量 PASS 标准（必须）

```
覆盖率 = md 已覆盖要点数 / PDF 要点总数
PASS 条件:
  - 覆盖率 ≥ 95%
  - 零占位标记（待补全/TODO/待后续/部分覆盖）
  - 行数/页数比值合理（本项目基准: ≈15-20 行/页）
```

### 规则 2：写/审必须分离（必须）

- 补写内容的 agent 和复核的 agent 不能共享上下文
- 复核 agent 必须独立读取 PDF + md，输出结构化覆盖率报告
- 已在 Issue 2 修复中验证有效

### 规则 3：AI 估算值必须标记（必须）

- 凡是 AI 无法程序化确认的数据（如 PDF 页码），标注 `(estimated)` 或 `(±N)`
- 不允许将估算值直接写入权威索引
- 需要精确值时，用程序化方法（逐页读取 + 关键词匹配）或人工核实

### 规则 4：人工抽样检查点（强烈建议）

- 每完成一个阶段，由用户随机抽取 3-5 个样本对照 PDF
- Issue 1 和 Issue 2 都是用户抽查发现的——这是唯一有效的兜底机制
- 关键是把"用户抽查"从偶然行为变成流程中的正式步骤

### 规则 5：红线类改动，派单时默认要求变异验证（必须）

> 补充于 2026-09-01，出处：联网参考通道分支（`feat/web-search-channel`，2026-08-31）

**规则 2 管的是"人写完由另一个人审"，规则 5 管的是"测试写完由谁来审"** —— 测试自己不会
报告自己没在测东西。

同一模式在该分支出现 **五次**，每次都只有靠变异才现形：

| # | 闸 | 失效方式 | 变异结果 |
|---|---|---|---|
| 1 | SSE 契约闸 | 正则抠空 → 空集 ⊆ 任何集合 → 永真式 | 抽空输入仍绿 |
| 2 | 前端字段读取闸 | 裸词 `in` 命中了注释里的同名词 | 删掉唯一读取点仍绿 |
| 3 | 生产接线闸 | 只查键在不在，无取值断言 | 两处改 `False`，1817 条全绿 |
| 4 | eval lever | 写死 `False`，无人断言其取值 | 改 `True`，1862 条全绿 |
| 5 | 反注入措辞 | 该句无任何断言引用 | 抽掉该句，1862 条无一响 |

> 基线数字随 task 落地增长，两个不同基线相邻出现，故标注来源：
> **1817 = `850fd13`**（Task 3 当时）；**1862 = `6445520`**（全分支终审的起始 HEAD）。
> 本项目硬规矩：**报告任何测量数字必须带 commit 号** —— 该分支在这一条上连栽三次。

共同点：**失败时的表现与成功时一模一样。** 不主动改坏它，它永远是绿的。

⚠ **第六次，发生在写这条规则的当天**（2026-09-01，`fix/eval-web-search-lever`）：为堵住
`--web-search` 命名陷阱而新写的 help 闸，自己就是裸 `in` 扫全文——把边界句整条删光、
再把锚点 token 塞进一个无关 flag 的 help，**9 条全绿**。它的注释还写着「锚点不许被精简掉」。
是独立复审做变异做出来的。⇒ **写下这条规则并不让你免疫它。**

⚠ **变异验证本身也会静默失效**（同日实测）：实现者的变异脚本用 `s.count(old) == 1` 定位一个
8 空格缩进的串，而 12 空格那行**包含**该子串 ⇒ `count == 2` 断言抛错，但 shell 循环继续，
于是拿**未变异的代码**跑出了一张"全绿"表。是它自己复查发现并重跑的。
⇒ **变异脚本必须自证变异真的打上了**（改完先 `grep` 回读、或比对 sha256），否则你验证的是
一个没被改坏的程序 —— 而它当然是绿的。裸子串定位 + 失败被吞，正是同一族形状。

**最要命的一层**：那次事故产出的"全绿"，**恰好等于它要证明的假设（lever 全裸）的预期输出**
⇒ 事故给出的是**假确认**，不是报错。这是"失败时的表现与成功时一模一样"**上升了一层**——
从被测对象升到**验证工具本身**。⇒ 变异验证也要问同样那个问题：
**如果我的变异根本没打上，这次运行的输出会跟现在有什么不同？** 答不出来就还没验证。

**同族的三种具体栽法**（2026-09-01 一天之内全撞上，都靠事后追查才发现）：

| # | 栽法 | 表现 |
|---|---|---|
| 1 | 裸子串定位失败被 shell 吞掉 | 变异没打上，拿原代码跑出"全绿" |
| 2 | **先加载页面、后改文件** | JS 不热重载，已运行的闭包用的还是改之前编译进内存的代码 —— 变异对它无效 |
| 3 | 用 `git checkout -- <file>` 还原变异 | 工作区有**未提交的修复**时，它撤销的不是变异而是**一切** —— 修复本身被静默冲掉，后续变异全跑在"没修过"的代码上 |

第 3 种最阴：前面的变异结论**看起来都成立**，因为它们确实红了——只是红的原因是"修复没了"而不是"闸抓住了"。

⇒ 通用对策：**变异脚本必须先自证变异真的作用在了被测的那份代码上**——改完 grep 回读、比 sha256、
前端则先改文件再加载页面；还原用**保存原始字节回写**，不用 `git checkout --`。

**为什么记在"派单"而不是"agent 自觉性"上**：实现者自陈——"我不是每次都想得起来做变异
验证，是你在派单时把『各做一次变异验证』写成硬要求，我照做时才撞见『删掉红线措辞 1862
条里没有一条会响』"。⇒ 靠自觉会漏，写进派单不会。

做法：派单文里写死"对 X 做一次变异验证，给出变异命令与真实输出"，而不是"记得测一下"。
适用范围＝**红线类改动**（对外质量背书数字、安全/反捏造措辞、生产接线开关）。

### 规则 6：闸失效分三类成因（B 含两个子型），按成因选对策（必须）

> 补充于 2026-09-01，同一出处

⚠ **本条初稿是错的，改正过程本身值得记**：初稿照搬了原始记录里「五条里有四条是同一个成因
（抽取端变空/变形 ⇒ 判定式恒真），对策是抽取端加尺寸下限」的论断。独立复审逐条验算后推翻：
**真正符合该成因的只有 2 条，而尺寸下限只对其中 1 条有效。** 三种成因被压成了一种，
后果是让人以为最贵的那一类（对外背书数字的接线）已被一个便宜对策覆盖——实际一点没覆盖。
⇒ 与规则 5 同源的元教训：**采纳一条归纳时，归纳本身也要先验算**，忠实转录不等于已验证。

规则 5 表里那**五条**分属 **A / B1 / C** 三类；另有一个子型 **B2** 不在那五条里，
但在本仓库有**四次**实测记录，且守着最承重的不变量，故一并列出。对策各不相同：

| 成因 | 案例 | 对策 | 尺寸下限管用吗 |
|---|---|---|---|
| **A. 抽取端变空/变形 ⇒ 判定式恒真** | #1 SSE 契约闸（抠空成空集）<br>#2 前端闸（裸词命中注释） | #1 抽取端加**尺寸**下限；<br>#2 要靠**形状锚**（`\b` 词边界、先限定作用域再断言） | #1 ✅ / #2 ❌ |
| **B1. 断言维度不全：断了键集/结构，没断取值** | #3 生产接线闸<br>#4 eval lever（写死 `False`） | **取值断言 + flag 的 ON/OFF 两个方向都钉**（只钉 ON，把值写死成常量照样绿） | ❌ 完全无效 |
| **B2. 断了相对关系（两边相等／差集为空），没断绝对值与方向** | prod↔eval 等价性闸<br>（本仓库**实测四次**静默通过） | 相等之后，**每一边再各自钉到绝对值**：<br>`cards["top_k"] == TOP_K and docs["top_k"] == 7`，<br>而不只是两边差集为空 | ❌ 完全无效 |
| **C. 根本没有闸** | #5 反注入措辞 | 只能靠规则 5 的**变异验证**发现 | ❌ 无从谈起 |

**成因 A 的对策**（最便宜，写的时候顺手就能加）：

```python
emitted = extract(...)
assert len(emitted) >= 6, "抽取端失效，下面的断言会变成永真式"
assert expected <= set(emitted)
```

**成因 B1 的对策**（本项目最贵的一类——它咬掉的是对外质量背书数字）：

```python
assert captured(["--flag"])["lever"] is True    # 方向一
assert captured([])["lever"] is False           # 方向二：缺了它，写死成常量照样绿
```

**成因 B2 的对策** —— 它是本仓库最爱静默失效的一种，且守着 prod/eval 等价性这条最承重的
不变量。`assert prod == eval` 式的闸**两边一起漂、或者对调时，断言一字不变**：

```python
assert cards["top_k"] == docs["top_k"]                  # 不够：对调照绿
assert cards["top_k"] == TOP_K and docs["top_k"] == 7   # 每边各钉绝对值，对调即红
```

⚠ 拿 `assert prod == eval` 式闸对照本表时容易误判：抽取端好好的（不是 A）、"我断了取值啊"
（以为不是 B1）、有闸（不是 C）⇒ **三类都对不上，于是判定自己没问题**。B2 就是为这种误判
而单列的。四次实测记录见 `sdtm-rag/scripts/tests/test_docs_engine_parity.py` 的行内注释
（**引函数名而非行号**）：

> ⚠ **行号在长效文档里有两种坏法，2026-09-01 一天之内两种都撞上了**：
> 1. **凭印象填、没回核** —— 下面这四条的初稿行号错了三个。
> 2. **写的时候是对的，被同一个 changeset 自己改废** —— spec 里引的 `run_eval.py:844/873/1054-1055`
>    在写入那一刻逐行正确，但同一批改动在其上游插了约 31 行，落库时已全部指错。
>    **这种校对当时发现不了**：你核过了，它是对的；失效发生在核完之后、提交之前。
> ⇒ 对策不是"更仔细地核行号"，是**别在长效文档里引行号** —— 引函数名、常量名、docstring 措辞
> 这类随代码一起移动的锚点。本项目的 spec 已按此清空全部行号引用。


| 记录位置 | 变异 | 结果 |
|---|---|---|
| `test_the_two_paths_hand_the_docs_engine_identical_structural_kwargs` docstring | 两条路径同时指到卡片库／同时开 S1／同时把席位读成 `args.top_k` | 相等断言照绿 |
| `test_eval_docs_engine_carries_every_lever_its_cards_engine_carries` | 两台 `top_k` **对调** | 差集一字不变，全量全绿 |
| 同上 | 四台 study 引擎 `embedding_model` **一起**换 bogus | 全量全绿 |
| `test_prod_docs_engine_carries_every_lever_its_cards_engine_carries` | 两台 `hybrid_alpha` **一起**改 0.99 | 全量全绿 |

**为什么 C 说明了规则 6 是规则 5 的补充而非替代**：成因 C 里根本没有断言可加下限，
只有主动改坏才会现形。A、B 两类可以在写的时候预防，C 只能靠事后变异挖出来。

⚠ 更直接的证据：本条规则落地当天（2026-09-01），复审顺着一段注释做变异，挖出
`eval/run_eval.py` 里的**兄弟 lever `prompt_guardrail` 是 B1 同款洞、就在隔壁 8 行**
—— 钉成常量 `True`/`False` 两个方向各 1874 条全绿，可以跑出**标着 `guardrail=ON`、
实际全程 OFF** 的 140q 数字。**一类缺陷极少只出现一处**：修好一个，立刻去看它的兄弟。

## 5. 适用场景

**规则 1-4** 适用于任何 **AI 辅助从非结构化源（PDF、扫描件、图像）提取结构化知识** 的项目。
**规则 5-6** 适用于 **AI 辅助写代码与测试**，尤其是改动落在对外质量背书数字或安全措辞上时——
它们与规则 1-4 同源（都是"自己判定自己完成了"），只是载体从 md 文件换成了测试断言。

> 与 `METHODOLOGY.md` 的对应关系（免得每次重新纠结"那边说 four，这边说 six"）：
> 该对外声明 §5 的 **four standing controls ＝ 本文规则 1-4**，出自知识库抽取线的两次
> non-conformance，陈述至今成立，**无需改动**。**规则 5-6 出自 RAG 代码线**，不属该声明
> 覆盖范围，故未并入。

核心原则是：

> AI 擅长找差异，不擅长判断"够不够"；擅长处理结构，不擅长衡量完整性。
> 同一条边界在代码上的样子是：**AI 写得出断言，但不会自己去问"这条断言在失效时还会不会绿"。**
> 把量化标准、写审分离、估算值标记、人工抽查、变异验证、按成因选对策这六个机制嵌入流程，
> 就能在保留 AI 效率优势的同时堵住系统性漏洞。
